# Captura: The 2026-07-28 Specification (Model Context Protocol Blog)

> Nota oficial de release de la especificación MCP `2026-07-28`. Se incluye como fundamento técnico del informe del 30 de octubre de 2026.

## Resumen

La especificación `2026-07-28` del Model Context Protocol introduce: núcleo de protocolo sin estado, Multi Round-Trip Requests, enrutado por cabeceras, resultados de listado cacheables, endurecimiento de autorización, un marco formal de extensiones y SDKs Tier 1 actualizados.

Desde la release de noviembre, MCP siguió creciendo: cerca de **medio billón de descargas al mes** en los SDKs Tier 1, con los SDK de TypeScript y Python cruzando el umbral de **1.000 millones de descargas totales**.

## Qué cambió

### Sin handshake ni sesiones

Se retiran oficialmente el intercambio `initialize`/`initialized` y la cabecera `Mcp-Session-Id` (SEP-2575, SEP-2567). Cada petición viaja por sí sola, llevando su versión de protocolo, identidad de cliente y capacidades en `_meta`. Existe una nueva RPC `server/discover` para que un cliente conozca las capacidades del servidor por adelantado (opcional). Cualquier petición puede aterrizar en cualquier instancia de servidor detrás de un balanceador round-robin simple, sin almacenamiento compartido.

Ejemplo de petición:

```
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search
{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search","arguments":{"q":"otters"},
 "_meta":{"io.modelcontextprotocol/clientInfo":{"name":"my-app","version":"1.0"}}}}
```

Eliminar la sesión a nivel de protocolo no obliga a la aplicación a ser sin estado: si el servidor necesita estado entre llamadas, acuña un handle explícito desde una tool y haz que el modelo lo devuelva como argumento. Esto funciona mejor que el estado de sesión oculto en el transporte, porque el modelo ve el handle y lo enhebra entre tools.

### Multi Round-Trip Requests (MRTR)

MRTR reemplaza las peticiones servidor→cliente `elicitation/create`, `sampling/createMessage` y `roots/list`, que antes exigían un stream bidireccional abierto. Cuando una tool necesita algo del usuario a mitad de llamada (una confirmación o un parámetro faltante), el servidor devuelve `resultType: "input_required"` junto con las peticiones que necesita respondidas, y el cliente reintenta la llamada original con las respuestas adjuntas en `inputResponses` (SEP-2322).

### Enrutado por cabeceras

Las peticiones Streamable HTTP ahora **deben** incluir `Mcp-Method` y `Mcp-Name` (SEP-2243). El gateway, el rate limiter o el WAF pueden enrutar y medir sobre esas cabeceras en lugar de parsear los cuerpos JSON.

### Listados cacheables

Las respuestas de `tools/list`, `prompts/list`, `resources/list` y `resources/read` ahora llevan `ttlMs` y `cacheScope` (SEP-2549), permitiendo al cliente decidir la mejor estrategia de caché y reducir re-fetch innecesario.

### Autorización

- Los servidores de autorización deben devolver el parámetro `iss` conforme a RFC 9207, y los clientes deben validarlo antes de canjear un código (SEP-2468). Cierra un agujero de confusión de servidor de autorización.
- Los clientes fijan `application_type` durante el Dynamic Client Registration (DCR) para que los servidores dejen de rechazar redirecciones `localhost` en apps de escritorio y CLI (SEP-837).
- Las credenciales de cliente quedan ligadas al emisor que las acuñó; sin reutilización entre servidores de autorización (SEP-2352).
- DCR queda formalmente **deprecado** en favor de Client ID Metadata Documents (CIMD). DCR sigue funcionando por compatibilidad, pero se eliminará en una versión futura.

### Tasks

Tasks sale del núcleo experimental y pasa a la extensión `io.modelcontextprotocol/tasks`, con `tasks/get` basado en polling y un nuevo `tasks/update` (SEP-2663). Las notificaciones de cambio pasan del antiguo endpoint HTTP GET a un único stream `subscriptions/listen` al que los clientes se suscriben por tipo de notificación.

### Deprecaciones

Roots, Sampling y Logging quedan deprecados (SEP-2577): siguen funcionando al menos doce meses, pero las nuevas implementaciones no deberían adoptarlos. El transporte legacy HTTP+SSE también queda oficialmente deprecado, con una ventana de salida de un año.

## SDKs

Los cuatro SDKs Tier 1 hablan `2026-07-28`: TypeScript, Python, Go y C#. El SDK de Rust lo soporta en beta. Habrá coste de migración, especialmente para quien dependía de los identificadores de sesión.
