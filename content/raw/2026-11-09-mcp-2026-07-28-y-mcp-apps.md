# MCP Protocol Updates: DCR, OAuth CIMD, Streamable HTTP & MCP Apps

TrueFoundry · Ashish Dubey · Updated November 6, 2026

## TL;DR

- The 2026-07-28 MCP specification changed four things at once — how clients register (DCR is deprecated for CIMD), how they talk to servers (Streamable HTTP replaces HTTP+SSE), how requests are routed (new `Mcp-Method` / `Mcp-Name` headers), and how servers ask for input mid-call (elicitation moves to Multi-Round-Trip Requests). Any team running MCP in production is affected.
- Dynamic Client Registration is deprecated in favour of Client ID Metadata Documents (CIMD). DCR still works for backward compatibility but will not be removed before July 2027. New integrations should not adopt it.
- Streamable HTTP is now stateless. The `initialize` handshake and `Mcp-Session-Id` are retired; each request carries its protocol version, identity and capabilities in `_meta`, so servers scale horizontally behind a load balancer — but lost in-flight requests are not resumed.
- Header-based routing is a gift to gateways. Because `Mcp-Method`, `Mcp-Name` and `Mcp-Param-*` headers now describe each request, a gateway can route, rate-limit and cache without ever parsing the JSON body.
- MCP Apps (`io.modelcontextprotocol/ui`) introduces interactive UI surfaces rendered by capable hosts — a new governance surface, because a server can now ship UI, not just text.
- A gateway absorbs most of this churn for you. Point your agents at one endpoint and the gateway speaks the new transport, enforces the new auth, and routes on the new headers — so a spec revision becomes a config change, not a fleet-wide rewrite.

## The 2026-07-28 release, in one view

Five changes carry almost all of the operational weight. The pattern is consistent: the protocol is shedding stateless-hostile machinery — session IDs, handshakes, dynamic registration — and replacing it with self-describing requests that any intermediary can route without holding state.

## Where teams get this wrong

- **They adopt deprecated primitives in new code.** DCR, Roots, Sampling and Logging all still work, so they look safe to build on. They are on a removal clock. New integrations should treat them as off-limits.
- **They trust headers they never validated.** Header-based routing only works because headers are read before the body.

## MCP Apps (extensión oficial `io.modelcontextprotocol/ui`)

- Estado: Stable (2026-01-26), primera extensión oficial de MCP. SEP-1865. Es **opcional** y debe negociarse explícitamente entre cliente y servidor mediante el mecanismo de capacidades de extensión.
- Los servidores declaran **recursos de UI** con el esquema de URI `ui://` y MIME `text/html;profile=mcp-app`; las herramientas los referencian mediante `_meta.ui.resourceUri` y un campo `visibility` (`"model"` o `"app"`).
- El host renderiza el recurso en un **iframe en sandbox** y la comunicación UI↔host va por JSON-RPC 2.0 sobre `postMessage`; los mensajes son auditables y el host puede exigir consentimiento del usuario para llamadas a herramientas iniciadas desde la UI.
- CSP restrictiva por defecto si `ui.csp` se omite: `default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self' data:; connect-src 'none'`.
- Capacidades del host negociables: `openLinks`, `downloadFile`, `serverTools`, `serverResources`, `logging`, `sandbox` (permisos camera/microphone/geolocation, dominios CSP), `updateModelContext`, `message`, `sampling`.
- La especificación construye sobre MCP-UI y el OpenAI Apps SDK; el paquete `@modelcontextprotocol/ext-apps` provee la clase `App`.
